# QuizUpdater

Нативное macOS-приложение для обновления Keynote-презентации квиза: превью всех
слайдов прямо в приложении, выбор нужного слайда кликом мыши, обновление таблицы
рейтинга и подстановка имён команд-призёров из Excel-файла, а также заполнение
карточек предстоящих игр данными с сайта расписания — вместо ручных запусков
Python-скриптов из терминала с номерами слайдов вслепую.

---

## 1. Задача, которую это решает

Ведущий квизов после каждого раунда считает баллы команд в Excel-таблице
(файл на Google Drive) и должен отразить это в презентации Keynote, которая
показывается на экране во время игры: обновить общую таблицу рейтинга и,
в конце игры, на слайдах-«визитках» призовых мест подставить название
команды-победителя вместо текста-заглушки.

Раньше это делалось так: два Python-скрипта (`update_keynote_rating.py`,
`update_keynote_names.py`) запускались из терминала, а номер нужного слайда
нужно было знать/помнить заранее и передавать флагом (`--slide 81`,
`--start-slide 182 --places 1 2 3 8`) — легко ошибиться, неудобно во время
живого мероприятия, когда счёт времени идёт на секунды между раундами.

QuizUpdater убирает эти два неудобства:
- **не нужно помнить номера слайдов** — они выбираются кликом по превью;
- **не нужен терминал** — обычное macOS-приложение с окном и кнопками.

При этом вся логика работы с Excel и Keynote — та же самая, что была
в скриптах (перенесена почти без изменений), так что поведение предсказуемо
и совместимо с уже отработанным на реальных играх процессом.

## 2. Архитектура: как это устроено

Приложение состоит из двух слоёв, которые вместе упакованы в один `.app`:

```
┌─────────────────────────────────────────────────────────────┐
│  QuizUpdater.app                                             │
│                                                                │
│  ┌───────────────────────┐        ┌──────────────────────┐   │
│  │   Swift / SwiftUI      │  JSON  │   Python-бэкенд       │   │
│  │   (интерфейс,          │◄──────►│   quiz_backend         │   │
│  │   Contents/MacOS)       │ stdout │   (Contents/Resources) │   │
│  └───────────┬─────────────┘        └───────────┬────────────┘   │
│              │ Process (subprocess)              │ osascript      │
└──────────────┼───────────────────────────────────┼────────────────┘
               │                                    ▼
               │                          ┌──────────────────┐
               │                          │   Keynote.app     │
               │                          │  (открытая        │
               │                          │   презентация)    │
               │                          └──────────────────┘
               ▼
      ~/Library/Caches/QuizUpdater/
      (кэш JPEG-превью слайдов)
```

**Почему два слоя, а не один язык.** Вся бизнес-логика (чтение Excel,
генерация и выполнение AppleScript) была уже написана, отлажена и проверена
на реальных играх на Python — переписывать её на Swift means риск незаметно
сломать рабочую логику ради красоты стека. Поэтому Python-логику просто
перенесли в отдельный модуль почти без изменений и переиспользовали, а Swift
отвечает только за интерфейс: превью слайдов, кнопки, кликабельный выбор.
Swift-приложение обращается к Python-бэкенду как к чёрному ящику — запускает
его как подпроцесс с аргументами командной строки и читает результат в виде
JSON из stdout.

**Почему Python встроен внутрь `.app`, а не Docker.** Изначально
рассматривался вариант "поднять бэкенд в Docker-контейнере", но это
принципиально не работает для этой задачи: управление Keynote идёт через
Apple Events/AppleScript, которые работают только между процессами прямо
на самом Mac — из Linux-контейнера Docker Desktop нет доступа ни к Keynote,
ни к `osascript`. Вместо этого Python и единственная его зависимость
(`openpyxl`, для чтения `.xlsx`) вендорятся (копируются) прямо внутрь
`Contents/Resources/backend` при сборке. Само приложение при запуске
использует системный `/usr/bin/python3` (тот, что ставится вместе
с Xcode Command Line Tools и есть на любом Mac, где вообще можно
разрабатывать/собирать софт) — пользователю не нужно ничего ставить:
ни conda, ни pip, ни Docker. Открыл `.app` — бэкенд "поднялся" сам как
дочерний процесс на каждый запрос.

**Почему AppleScript, а не какой-то API Keynote.** У Keynote нет отдельного
API для управления открытым документом — единственный официальный способ
скриптово взаимодействовать с уже открытой презентацией на экране (не
с файлом на диске, а именно с «живым» документом, который видит зритель) —
это AppleScript-словарь приложения (Standard Additions + Keynote Suite).
И старые скрипты, и новый бэкенд используют один и тот же механизм: Python
собирает текст AppleScript-программы и выполняет её через системную утилиту
`osascript`.

## 3. Технологический стек

| Компонент | Технология | Почему |
|---|---|---|
| Интерфейс | Swift + SwiftUI, Swift Package Manager (без `.xcodeproj`) | нативный вид/ощущение Mac-приложения; SwiftPM собирает universal binary одной командой без танцев с Xcode-проектом |
| Автоматизация Keynote | AppleScript через `osascript` | единственный способ управлять уже открытым документом Keynote |
| Чтение Excel | Python + `openpyxl` | чистый Python, не требует компиляции под архитектуру — легко «вендорить» в бандл |
| Связь Swift ↔ Python | `Process` (Foundation) + JSON по stdout/stdin | простой, отлаживаемый контракт: каждую команду бэкенда можно вручную запустить и проверить из терминала |
| Превью слайдов | AppleScript-команда Keynote `export ... as slide images` → JPEG, кэш на диске | сам Keynote умеет рендерить слайды в картинки, велосипед не нужен |
| Упаковка | Makefile: `swift build --arch arm64 --arch x86_64` + `codesign --sign -` (ad-hoc) | universal binary без Apple Developer-аккаунта — для личного использования на двух своих Mac этого достаточно |

Целевая платформа — macOS 13 (Ventura) и новее, Intel и Apple Silicon
(один и тот же файл `.app` работает на обоих благодаря universal binary).

## 5. Как это работает «под капотом»

### 5.1 Контракт между Swift и Python

Swift запускает Python как обычный подпроцесс:

```
python3 -m quiz_backend <подкоманда> [--аргументы...]
```

Бэкенд **всегда** печатает в stdout ровно один JSON-объект и ничего больше
(предупреждения библиотек уходят в stderr, не мешая парсингу):

```jsonc
// успех
{"ok": true, /* поля, зависящие от подкоманды */}

// ошибка — понятный русский текст + машиночитаемый код
{"ok": false, "code": "AUTOMATION_DENIED", "error": "Нет разрешения на управление Keynote..."}
```

Swift сначала декодирует только `{ok, code, error}`, чтобы понять — это
успех или ошибка, и лишь потом (если `ok: true`) декодирует полный,
специфичный для команды набор полей. Так интерфейс всегда может показать
пользователю понятную русскую ошибку, даже если сама подкоманда упала
с исключением где-то в середине работы.

### 5.2 Подкоманды бэкенда

| Подкоманда | Что делает | Ключевые аргументы |
|---|---|---|
| `list-documents` | Список открытых в Keynote документов и число слайдов в каждом | — |
| `read-excel` | Читает таблицу рейтинга из `.xlsx` | `--path` |
| `export-previews` | Экспортирует все слайды документа как JPEG (через `export ... as slide images` в Keynote) | `--doc`, `--out` |
| `update-rating` | Записывает данные из Excel в таблицу на выбранном слайде | `--doc`, `--slide`, `--excel`, `--max-rows`, `--dry-run` |
| `replace-names` | Заменяет текст-плейсхолдер «ЗАМЕНИТЬ» именами команд на выбранных слайдах | `--doc`, `--excel`, `--pairs "место:слайд,..."`, `--dry-run` |
| `fetch-schedule` | Загружает список предстоящих игр с сайта расписания | — |
| `fill-schedule-slots` | Заполняет карточки игр текстовыми полями на выбранном слайде | `--doc`, `--slide`, `--games '<json>'`, `--dry-run` |

Каждую команду можно запустить и проверить прямо из терминала — это
основной способ отладки, если что-то в приложении ведёт себя не так:

```bash
cd quiz
PYTHONPATH=backend:backend/vendor python3 -m quiz_backend list-documents
PYTHONPATH=backend:backend/vendor python3 -m quiz_backend update-rating --slide 81 --dry-run
```

Коды ошибок, которые бэкенд может вернуть: `EXCEL_NOT_FOUND`,
`EXCEL_BAD_FORMAT`, `KEYNOTE_NOT_RUNNING`, `DOC_NOT_FOUND`,
`APPLESCRIPT_ERROR`, `AUTOMATION_DENIED`, `INVALID_ARGUMENT`. Интерфейс
показывает соответствующий текст в статус-баре внизу окна; для
`AUTOMATION_DENIED` там же появляется кнопка «Открыть настройки».

### 5.3 Превью слайдов и кэш

По кнопке «Обновить превью» приложение вызывает `export-previews`, который
одной AppleScript-командой просит Keynote отрендерить все слайды документа
в JPEG во временную папку (Keynote сам её создаёт). Для презентации на
~200+ слайдов это занимает 30–50 секунд — прогресс-бар в приложении в это
время просто считает, сколько файлов уже появилось в папке.

Результат кэшируется в `~/Library/Caches/QuizUpdater/<хэш_имени_документа>/`.
При повторном открытии того же документа (если число слайдов не
изменилось) превью подгружаются из кэша мгновенно, без повторного
экспорта. Кнопка «Обновить превью» сбрасывает кэш принудительно.

### 5.4 Разрешение на управление Keynote (TCC)

При первом реальном обращении к Keynote macOS покажет системный диалог:
«QuizUpdater хочет получить доступ для управления Keynote» — это стандартная
защита macOS (Automation/TCC), а не ошибка приложения. Нужно один раз
нажать «Разрешить». Управляется в Настройки → Конфиденциальность
и безопасность → Автоматизация.

Поскольку приложение подписано ad-hoc-подписью (без Apple Developer
аккаунта — не нужен для личного использования), эта подпись меняется
при каждой пересборке `make app`, и macOS будет заново спрашивать
разрешение после каждой пересборки. Для повседневного использования
(без пересборок) разрешение запоминается один раз.

### 5.5 Карточки расписания игр — как это устроено

Режим «Расписание игр» заполняет на выбранном слайде до 4 «карточек» предстоящих игр
данными с сайта `sofia.quizplease.ru` (реальный JSON API `api.quizplease.com`, без браузера/JS).

**Важное техническое ограничение Keynote**, определившее весь дизайн: AppleScript в этой
версии Keynote не может ни создать новую фигуру/группу с нужным цветом (`shape`/`group` не
имеют свойств заливки/обводки/скругления), ни продублировать существующую (`duplicate`
работает только для целых слайдов, не для фигур/таблиц — «Shapes can not be copied»). Поэтому
приложение ничего не рисует и не копирует — оно только находит и заполняет текстом уже
существующие на слайде текстовые поля, которые пользователь готовит сам:

1. На выбранном слайде вручную (обычный Text tool в Keynote, без группировки и без Cmd+G)
   создаются **4 пары** текстовых полей: левое поле каждой пары — под тему+номер игры,
   правое — под дату, примерно на одной высоте друг с другом. Остальной контент слайда
   (заголовок, фон, футер) не трогается.
2. Приложение находит эти пары **по расположению**, а не по содержимому текста: все
   текстовые поля слайда группируются по Y-координате (в пределах допуска — Keynote слегка
   двигает рамку поля при автоподгонке под контент), декоративные надписи (заголовок и т.п.)
   остаются «строкой» с одним элементом и отбрасываются, а пары полей — «строкой» из двух
   элементов, где левый по X — тема, правый — дата.
3. Найденные пары сортируются по (Y, X) → это и есть слоты 1–4 (сверху вниз, слева направо).
   Игры (уже отсортированы по дате) занимают слоты по порядку; если игр меньше 4 — лишние
   слоты просто очищаются (пустой текст), если больше — показываются первые 4 по дате.
4. Размер шрифта левого поля подбирается автоматически (`schedule.compute_card_font_size`):
   короткий текст (`#NN`) — как в шаблоне, длинная тема — пропорционально мельче (не меньше
   16pt), чтобы не вылезать за рамку карточки.

Поскольку идентификация — по позиции, а не по уникальному тексту-маркеру, повторный запуск
полностью безопасен и идемпотентен: старый текст просто заменяется новым, ничего не
накапливается и не нужно ничего удалять вручную перед следующим прогоном.

## 6. Сборка

Нужен полный Xcode (не только Command Line Tools) — для universal-сборки
под arm64+x86_64, и любой Python 3 с `pip` на машине, где собирается
приложение (нужен только на этапе сборки, чтобы скачать `openpyxl`
в `backend/vendor/`; пользователю при использовании собранного `.app`
ничего ставить не нужно).

```bash
make app     # соберёт dist/QuizUpdater.app (universal binary, ad-hoc подпись)
make run     # то же самое + сразу открыть приложение
```

Проверить, что бинарь действительно universal:
```bash
lipo -archs dist/QuizUpdater.app/Contents/MacOS/QuizUpdater   # ожидается: x86_64 arm64
```

Тест самого бэкенда системным Python 3.9 (та же версия, что использует
бандл — на случай, если код случайно используется синтаксис новее):
```bash
make test-backend
```

### Разработка (без пересборки `.app` на каждое изменение)

```bash
QUIZ_BACKEND_DIR="$(pwd)/backend" swift run --package-path app
```

В этом режиме ответственным за Apple Events (и разрешение TCC) будет
терминал, а не `QuizUpdater.app` — финальную проверку разрешений делайте
через `open dist/QuizUpdater.app`.

## 7. Перенос на другой Mac (в т.ч. Intel)

**Вариант 1 — собрать на месте (надёжнее всего):**
```bash
# скопировать репозиторий на целевой Mac любым способом, затем:
make app && make run
```

**Вариант 2 — перенести уже собранный `.app`:**
- через scp/USB/локальную сеть — работает сразу;
- через AirDrop/скачивание из интернета — macOS помечает файл атрибутом
  quarantine, Gatekeeper заблокирует запуск ad-hoc-подписанного
  приложения. Снять карантин на целевом Mac:
  ```bash
  xattr -dr com.apple.quarantine /Applications/QuizUpdater.app
  ```

На целевом Mac должен быть Python 3 (для запуска уже собранного
бэкенда) — проще всего через Command Line Tools:
```bash
xcode-select -p || xcode-select --install
```
Устанавливать `openpyxl` на целевой машине не нужно — он уже внутри `.app`.

## 8. Использование

1. Откройте нужную презентацию `.key` в Keynote (как обычно).
2. Откройте `QuizUpdater.app` — вверху выберите документ Keynote и
   Excel-файл с рейтингом (по умолчанию подставлен путь на Google Drive),
   нажмите «Обновить превью».
3. **Режим «Таблица рейтинга»**: кликните по слайду с таблицей рейтинга
   на превью слева, задайте число команд (стрелочки «Команд: N»),
   нажмите «Проверить» — приложение покажет, что будет записано, ничего
   не меняя в Keynote, — затем «Обновить таблицу».
4. **Режим «Имена призёров»**: отметьте нужные места галочками, кликните
   по слайду 1-го места на превью — остальные места назначатся по
   убыванию автоматически (можно поправить вручную стрелочками у каждой
   пары), «Проверить» подсветит на превью зелёным/красным, найден ли
   на слайде текст-плейсхолдер «ЗАМЕНИТЬ», затем «Заменить имена».
5. **Режим «Расписание игр»**: нажмите «Загрузить расписание» — появится
   чек-лист предстоящих игр (можно снять галочку с ненужной), кликните
   по слайду с 4 подготовленными парами текстовых полей (см. раздел 5.5 —
   слайд готовится один раз вручную), «Проверить» покажет предпросмотр
   заполнения слотов, затем «Заполнить карточки».

Рекомендуется на новой/незнакомой презентации сначала пройтись
«Проверить» (dry-run) — это ничего не меняет в Keynote, только
показывает, что будет сделано.

## 9. Формат Excel-файла

Лист `Лист1`, данные со 2-й строки (первая строка — заголовки), чтение
останавливается на первой пустой строке:

## 10. Структура таблицы рейтинга в Keynote

На целевом слайде — две таблицы: «Таблица 1» (данные, без заголовка,
10+ строк × 10 колонок — именно её обновляет приложение) и «Таблица 2»
(заголовки, приложением не изменяется).

## 11. Известные ограничения

- Экспорт превью ~180–230 слайдов занимает 30–50 секунд (один
  AppleScript-вызов без промежуточных колбэков — прогресс-бар считает
  уже созданные файлы, честного процента от Keynote получить нельзя).
- Кэш превью на диске инвалидируется только по числу слайдов документа;
  если содержимое слайдов поменялось без изменения их количества —
  нажмите «Обновить превью» вручную.
- Файл на Google Drive может быть незагружен локально при первом
  обращении — возможна задержка и/или отдельный запрос доступа к файлам
  от macOS.
- Ad-hoc подпись означает, что TCC-разрешение на управление Keynote
  запрашивается заново после каждой пересборки `make app` (см. раздел 5.4).
- **Расписание игр**: жёсткий лимит 4 карточки на слайд (лишние игры не показываются,
  учитываются первые 4 по возрастанию даты). Автоподбор размера шрифта учитывает только
  длину текста темы, но не реальную ширину текстового поля в Keynote — если поле узкое
  (сделано под короткое «#NN»), длинная тема всё равно может выглядеть мелко/переноситься
  на несколько строк; для лучшего результата расширьте это текстовое поле в Keynote вручную.
